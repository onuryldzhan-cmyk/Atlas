This gave the **main session** — not just the intended subagent — full read/write tool reach into the vault (`mcp__filesystem__read_file/write_file/edit_file/move_file/create_directory/...`). No checkpoint or governance record documented this registration; it predates this session (present in the very first system-reminder of the prior conversation turn, before any action was taken) and is presumed leftover from earlier manual testing. With the user's explicit confirmation (chose "Kaydı şimdi kaldır" via AskUserQuestion in the prior turn), removed it: `claude mcp remove filesystem` → "Removed MCP server \"filesystem\" from local config"; `claude mcp list` now reports "No MCP servers configured".
2. **Verified this session's live tool surface still exposes it.** Re-ran `ToolSearch` for `"filesystem"` in this same running session after the removal and got full schemas back for all 14 `mcp__filesystem__*` tools (including `write_file`, `edit_file`, `move_file`, `create_directory`). The config-level fix does not retroactively unload an already-established MCP connection from a running session — this session's underlying process connected to that server before the registration was removed. A session restart is required for this session's own tool surface to actually drop `mcp__filesystem__*`.
3. **Diagnosed the wrong-directory bug and ruled out two hypotheses with direct evidence, rather than guessing.**
   - *Hypothesis A (quoting loss in the `cmd /c npx ...` chain for the space in "Atlas Memory") — REFUTED.* Wrote a standalone Node script (`child_process.spawn('cmd', ['/c','npx','-y','@modelcontextprotocol/server-filesystem@2026.7.10','C:\\Users\\HUAWEİ\\OneDrive\\Masaüstü\\ATLAS_CODEX_COMPLETE_LATEST_STATE_2026-07-30\\Atlas Memory'])`, i.e. the exact `command`/`args` pair from the agent file) and ran it directly (Node v24.20.0, confirmed via `node --version`). It worked correctly: the server's own stderr logged `allowed directories set from server args: ['C:\...\Atlas Memory']` — the single correct path, not split, not mangled. Two further variants were also tested in the same script: invoking `npx.cmd` directly without the `cmd /c` wrapper failed immediately with `spawn EINVAL` (confirms why the original author needed the `cmd /c` wrapper at all); joining everything into one pre-quoted string arg after `/c` produced visibly garbled, cwd-prefixed path fragments — a different, worse failure mode than what the real subagent exhibits, useful as a negative contrast.
   - *Hypothesis B (wrong/unsupported YAML schema for inline per-agent `mcpServers`) — REFUTED.* Consulted the `claude-code-guide` subagent with the exact current frontmatter and the isolation evidence above. It confirmed: inline per-agent `mcpServers` is an officially documented, supported feature, and the current YAML shape (`mcpServers:` as a list containing one single-key map, e.g. `- obsidian-vault: {...}`) is exactly the documented-correct form — not a schema error.
   - *Isolating experiment (content-independence test) — this pinpointed the actual bug.* Temporarily edited `.claude/agents/atlas-obsidian-writer.md`'s `args` to point at a freshly created, pure-ASCII, space-free scratch directory (`.../scratchpad/mcp_diag_nospace/`, containing a `MARKER.txt`) instead of the real vault path, then re-invoked the real `atlas-obsidian-writer` subagent (a fresh `Agent` call, not a continuation, so the edited frontmatter would actually be picked up) and had it call `list_allowed_directories` then try to read `MARKER.txt`. Result: it **still** reported the allowed directory as the repo root (`...SOURCE_REPOSITORY\SOURCE_REPOSITORY`), not the scratch directory, and `MARKER.txt` read failed with `ENOENT` in the repo root — the identical failure signature as with the real vault path. Since the only variable changed was the path's content (removing both the space and reducing Unicode-in-username dependence), and the failure was unchanged, the bug is **not** related to the path's content at all.
   - **Conclusion:** on this installed CLI build, the trailing directory argument is not reaching the spawned `server-filesystem` process at all for agent-scoped inline stdio MCP servers — the server falls back cleanly to its own `process.cwd()` (the project root, which Claude Code evidently sets as the subprocess's working directory). This is a CLI-build-level limitation/bug, not a fixable repository config error, and is exactly what the original commit's own caveat ("unverified on installed CLI build until restart") anticipated. `claude-code-guide` recommended, if this turned out not to be a config mistake, filing it as a bug via `/feedback`.
